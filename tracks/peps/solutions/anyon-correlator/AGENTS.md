## 研究与计算

- 用户研究路线以中文 `PLAN.md` 为准；当前结果看 `README.md`、`M2_REPORT.md`、`M3_REPORT.md`。
- simple update 与 AD 是不同算法，分别放在 `simple-update/` 和 `ad/`；不同表示和更新方法也要写明。基态以 loop/cluster update 为主，AD 为备用和比较。
- H=−ΣA−ΣB−hₓΣX−h_zΣZ，Pauli convention，Jₑ=Jₘ=1；无限方格，spins on edges，能量按边自旋归一化。
- 区分解析初态、随机初态、已有数值态的继续优化和增大 D 的延续；不把一个起点成功推广为任意随机寻优成功。

- 现有 `results/` 是本地原始数据，许多文件不在 Git；不要覆盖已有计算。`frozen_states/` 中的 JSON 可移植状态与原 binary 对照保留。
- 不将未收敛环境、小梯度、低能量或权重稳定单独解释成正确基态；同一张量的不同测量分支不能按最低能量选取。
- 旧集群信息已过时，禁止自动连接、修复或提交。需要额外资源时先向用户说明；本地长任务必须有预算、进度和保存点。
- Julia 环境用仓库根 `--project=julia-env`；不要为整理文件升级包或重新解析环境。根 `make test` 不代替本项目 Julia 测试。
- 按实际改动选择检查。整理后的测试已通过、数值程序又未修改时，不仅为了 commit/push 重跑完整 Julia 测试；核对文件内容、路径和待提交改动即可。重算基态、磁场扫描与软件测试分开安排。

## 科研文档与技术说明的写作规范（必须遵守）

本项目涉及凝聚态物理、量子多体理论和张量网络数值计算。所有 README、研究报告、算法说明、开发计划以及面向用户的技术解释，都必须遵循以下规范。

### 1. 读者背景与写作目标

默认读者是一名熟悉量子多体理论、PEPS、MPS、CTMRG 等基本概念的理论物理研究者，但不熟悉当前项目的源代码、内部数据结构和实现历史。

- 可以直接使用标准的物理、数学和张量网络术语。
- 对项目中特有的概念、数据结构、算法步骤和命名，必须在首次出现时解释其具体含义。
- 不要假设读者已经阅读过源代码，或者知道某个函数内部执行了什么操作。
- 文字应当具有学术准确性，同时保证读者能够理解每一步的数学与物理意义。

**核心要求：读者应当仅通过阅读文档，就能理解算法的基本原理、主要计算流程及其合理性，而不需要反复查看源代码或追问术语的含义。**

### 2. 解释算法时，必须交代操作过程和原因

描述一个数值算法或计算步骤时，应当尽可能回答以下问题：

1. **对象是什么？** 涉及哪些张量、指标、算符或物理量？它们分别代表什么？
2. **具体做什么？** 张量如何收缩、算符如何作用、怎样进行分解或截断、更新后得到什么？
3. **为什么这样做？** 该步骤在数学或物理上有什么作用？为什么有必要？
4. **如何验证？** 如果涉及近似、截断、对称性约束或规范变换，如何判断结果正确？

对于关键算法，适当使用数学公式、指标表达式或简明的计算流程说明。

对于复杂步骤，可以分段详细解释。**不要为了追求简洁而省略理解算法所必需的内容。**

### 3. 避免含糊、压缩和仅对开发者有意义的表述

禁止用模糊的概括代替具体说明，例如：

- 「统一局部因子」
- 「补偿不同 λ 的变化」
- 「在两端配对变换虚拟基底」
- 「区分不同位置」
- 「消除简并基底的歧义」
- 「避免标签冲突」

这些表述并非一律不能使用，但必须说明所指对象、具体操作，以及相关的数学意义。

尤其注意：

- 「两端」「不同位置」「同类」「局部」等词必须具有明确指代。
- 若引入「局部因子」「加权张量」「工作数组」等名称，应明确其定义及与原始 PEPS 张量的关系。
- 对于 gauge transformation、symmetry projection、truncation 等操作，应区分数学定义、数值实现及其对物理态的影响。
- 不要混淆张量类型的数量、独立参数的数量、物理指标的数量、虚拟指标的数量和 bond dimension。
- 描述对称性时，明确说明对应的群作用及指标置换关系。例如循环旋转不变性不等同于任意指标交换不变性。

如果某个概念确实复杂，可以增加解释篇幅。不要创造未经定义的缩写、比喻或程序内部术语来压缩说明。

### 4. 以物理和数学为主线组织文档

研究文档应当优先说明：

- 研究的模型、目标和对称性假设；
- 张量网络的具体结构与参数化方式；
- 数值算法的原理及主要步骤；
- 计算结果、误差、收敛性和物理验证；
- 必要的实现说明与复现方法。

程序实现细节（例如函数名称、文件路径、checkpoint、JSON 字段、异常处理和日志格式）可以保留，但应放在合适的位置，不要让它们取代算法解释。

涉及软件工程的内容，应当说明其实际作用；不必将每一个内部实现细节都写进研究性 README。

### 5. 保持自然、严谨的学术表达

- 使用完整、连贯的句子，明确交代前后步骤之间的逻辑关系。
- 避免过度压缩的技术短句和难以理解的术语堆叠。
- 避免频繁使用「不是……而是……」「不声称……」「不意味着……」「不能误认为……」等防御性或对比性表达。
- 确实重要的适用范围、数值局限与潜在错误，应当明确说明，可以集中放在结果讨论或局限性部分。
- 不要为了展示严谨性而反复列举没有采用的方案、没有作出的主张或无关的历史实现。
- 不要使用生造的比喻、拟人化描述或不符合物理学论文习惯的表达。
- 不要滥用表格和层层嵌套的小标题。优先使用连贯的段落组织论述。
- Markdown（`.md`）文档可以使用 LaTeX 公式。数学排版遵循学术习惯：简单符号及短公式使用 `$...$` 行内公式，较长方程或连续推导使用独立成段的 `$$...$$` 行间公式。
- 在 OpenCode 对话中，数学表达使用 Unicode 字符和普通文本公式，不输出 LaTeX 命令或公式定界符。文档排版与对话输出分别遵守上述要求。

### 6. 准确性优先，不允许用含糊语言掩盖不确定性

文档中的算法描述必须与实际代码一致。

- 如果不确定某个函数究竟执行了哪些步骤，应先阅读相关实现，再进行解释。
- 不要根据函数名猜测算法。
- 不要把数值上的经验性成功描述为已经得到数学证明。
- 不要混淆张量满足某种对称性、数值表示满足规范条件，以及最终物理态具有该对称性这几个不同层次。
- 对尚未验证的结论应明确说明，而不要用复杂措辞回避问题。

### 7. 提交文档前必须进行可读性自查

完成 README、研究报告或算法说明后，重新站在一名没有读过本项目代码的理论物理研究者的角度检查：

1. 有没有未经解释的项目专有术语？
2. 有没有读者无法确定所指对象的代词或抽象名词？
3. 有没有只列出函数名，却没有解释实际数学操作的地方？
4. 有没有只说明「做了什么」，却没有解释「为什么这样做」的重要步骤？
5. 有没有将多个非平凡操作压缩成一句话，导致读者难以理解计算流程？
6. 有没有可能引起物理或数学误解的不严谨表述？
7. 有没有与理解主要算法无关的防御性声明或实现细节？

发现上述问题，应当直接修改文档，而不要等待读者指出。

**最终原则：准确性、可理解性和逻辑完整性优先于文字简短。文档要让研究者理解实际的数学和物理计算，而不能只是对程序执行过程的高度压缩概述。**
